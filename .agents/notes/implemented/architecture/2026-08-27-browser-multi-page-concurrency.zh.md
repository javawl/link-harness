# Agent Note: 浏览器多页寻址与页内并发

Status: implemented

[English](2026-08-27-browser-multi-page-concurrency.md) | 中文

## Problem

外链批次只能逐条发布，因为每条浏览器命令都落在"活动页"上：服务定义把全部命令串行过一条全局链，Playwright Provider 只寻址最近打开的标签页，模型侧工具也没有命名标签页的途径。批次总耗时等于各条目之和——包括每次等验证邮件和每次选错选择器的超时——而各站点彼此独立，串行掉的绝大多数是等待而非工作。再开一个浏览器会话会复制 cookie 罐（谷歌会话、站点登录全部要再来一遍）并放大反爬暴露面，是错误的药方。

## Decision

以标签页（而非会话）作为既有单一持久会话上的并发单元：

1. 每条 `BrowserCommand` 增加可选 `page` 引用（`BrowserPageAddress`）。navigate 以调用者命名的新引用打开并绑定标签页；后续命令按引用寻址该页；命名未知或已关闭引用的命令响亮失败。不带引用的命令保持"最近标签页"旧契约，存量单页调用方不受影响。
2. 服务定义去掉全局命令链：命令直接分发到惰性打开（单飞）的会话上；保序职责移入 Provider。
3. Playwright Provider 为每个被寻址的标签页维护一条串行链。同页命令保持分发顺序；不同页命令重叠。站点弹出的窗口与持久上下文残留页自动收养为可寻址页；标签页关闭（无论我方还是站点）即丢弃引用。
4. 模型侧工具把 `page` 参数贯通所有动作，在每次页面捕获里返回引用（`[page pN] 标题`），并在提示词章节里写明引用纪律。单个 agent 自己的调用保持串行（`isConcurrencySafe` 为 false）；跨 agent 并发属于编排——backlink-publish 技能按域名分组派发条目，每个子 agent 寻址自己的引用，共享同一个 cookie 罐和同一个租约。

## Consequences

- cookie 状态保持共享且单一：一个谷歌会话、一套站点登录、磁盘上仍只有一个 profile。
- 同站动作在构造上（每页一链）与技能规则上（条目按域名分组）都保持串行，保住按域名的节奏控制。
- 闭合的 `BrowserCommand`/`BrowserResult` 联合只是加了字段而非成员；Provider 与消费方依旧按穷举 switch 编译。
- 混用风格时，无引用的旧式命令会与按引用命令交错；契约规定并行调用方必须对一切命令使用引用，技能的子任务提示词强制执行。
- 对混合批次的实测效果：等邮件与慢页面在不同条目间重叠（批次墙钟时间从"各条之和"逼近"最慢条目组"）。

## Alternatives considered

- **多个持久上下文（每个工作者一个 profile）** —— 复制 cookie 罐与谷歌播种，放大反爬暴露面；作为错误的复制对象被否决。
- **保留全局链、只并行模型推理** —— 页面工作仍串行，占大头的页面等待与邮件轮询毫无改善。
- **`connectOverCDP` 连用户机器上的远程浏览器** —— 解决的是浏览器在哪的问题，且引入网络信任边界；不属于进程内吞吐的范畴。
